# 鸣潮对决项目协作规则

## 进入项目时的必读顺序

每个新的 AI 对话或 Agent 第一次进入本项目时，必须先完成以下读取，再执行修改、打包或部署：

1. 读取项目根目录 `PROJECT.md`，了解项目目标、当前主要内容、目录职责和交付方式。
2. 枚举并完整读取 `rules/` 下全部 Markdown 文件；不得只凭对话历史、记忆摘要或文件名推测规则。
3. 只有任务需要了解历史改动时，才按下方约定读取 `changes/`，不得把 `changes/` 设为每次进入项目的强制全量读取项。

## 所有更新必须先备份

- 任何代码、文档、规则、素材、配置、安装包或部署内容的更新，均必须先备份明确的修改对象，再开始制作新版本。
- 备份默认放入 `archives/backups/{任务名}-YYYYMMDD-HHMMSS/`；修改前必须核对备份文件存在，重要文件需核对 SHA-256 一致。
- 新版本使用新的时间戳、版本号、目录或部署记录；不得覆盖历史安装包、已归档版本或用户指定的参考包。
- 备份不等于交付。修改完成后仍需按任务风险执行测试、验包、归档或线上核验。

## 对话中的规则意图必须沉淀

- 用户在对话中表达明显、可复用的限制或强制要求时，必须在本轮任务结束前写入合适的 `rules/*.md`，避免后续对话遗忘。
- 典型规则意图包括但不限于：
  - “不要修改/不要执行某件事”；
  - “每次必须先做某件事”；
  - “只允许修改某个范围，其余不动”；
  - 对备份、验证、打包、部署、素材使用、UI 保留或数据安全提出的长期要求。
- 新规则应写清适用范围、触发条件和例外，不得只记录脱离上下文的一句话。
- 一次性的数值选择、临时测试参数或仅对当前操作有效的指令，不应误写成长期规则；无法判断是否长期有效时，先向用户确认。
- 若新要求与既有规则冲突，应先向用户说明冲突并确认，以最新明确确认结果更新规则，不得让两条冲突规则长期并存。

## PROJECT、rules 与 changes 的职责

- `PROJECT.md`：只维护项目的主要内容，包括项目目标、交付边界、当前核心能力、目录结构、运行方式、验证入口和发布流程。
- `rules/`：维护必须持续遵守的玩法规则、工程限制、用户长期约束和协作规范。
- `changes/`：记录已经执行的重要变更、验证证据、部署版本和剩余风险；不作为项目主要内容或长期规则的唯一来源。

## changes 的读取边界

只有以下情况需要读取 `changes/`：

1. 当前 AI 对话第一次读取本项目，且当前任务确实需要了解过去做过什么、为什么这样实现或目前进度从何而来；此时只读取与任务相关的最近记录，不要求全量扫描。
2. 用户在对话中明确提到过去的修改、历史版本、部署记录、修复记录或要求对比/延续过往变更。
3. 当前任务必须依赖历史变更证据才能安全执行，例如定位回归来源、确认曾部署版本或避免重复修复。

普通问答、明确范围的小修改，或者仅凭 `PROJECT.md` 和 `rules/` 已足够完成的任务，不需要读取 `changes/`。

## 移动端横屏可见性

- 适用范围：`mobile/` 的横屏菜单、设置页、弹层和局内功能面板。
- 任何功能控件都不得因固定高度配合 `overflow: hidden` 被裁切或变成不可访问；优先让内容在当前可用高度内完整呈现，无法同时容纳时必须提供清晰可用的内部滚动兜底。
- 界面缩放只用于偏好与空间优化，不能作为避免控件遮挡的唯一方案；先保证可访问性，再应用缩放。
- 新增或调整横屏布局时，至少在 `852 × 343` 的紧凑横屏下检查关键操作控件完整可见。

## 手机版内容回迁到桌面 HTML

- 当用户指定某个手机版安装包作为桌面 HTML 的参考版本时，只回迁该版本相对桌面新增的卡牌、卡面资源和与这些卡牌直接相关的玩法规则。
- 不回迁移动端专属布局、菜单缩放、PVP 房间/服务端、部署配置或无关重构；已有桌面功能与界面保持不变。
